# PostgreSQLプラグイン 0.2.0

同じchannelへの送信を並行処理し、履歴が増えた場合や統計が古い場合の受信・再生SQLを改善しました。ACK済みフレームの保持期限も設定できます。

- ノード登録との排他を維持したまま送信を共有ロックへ変更し、登録・送信の分離レベルをREAD COMMITTEDに固定しました。
- 受信は配送対象の主キーを参照し、古い統計による履歴の全走査を避けます。初回再生には期間索引を使います。
- `retention_ms`・`cleanup_interval_ms`・`cleanup_batch_size`を追加しました。自動削除は既定で無効です。全登録ノードが有効にした場合だけ、最長の保持・再生期間を過ぎたACK済みフレームを削除します。未ACKは保持します。
- 古いACKが、期限切れ削除後に同じUUIDで登録された新しい配送を消さないようにしました。
- PostgreSQL 16・17・18の実DB試験と実行計画の回帰検証をCIで実行します。タグのCI成功後、実行ファイル・manifest・SQL・SHA256SUMSを公開します。

3ノード・1400バイト・128件バッチの比較では、合計約54.7Mbpsから179.1Mbpsへ改善しました。PostgreSQL 17.11、4CPU/2GiBのコンテナ、loopback・TLSなしで各条件3回の中央値です。本体・IPC・NICは含みません。72試行で884,736配送、保持を有効にした約5分の試験で3,366,912配送の内容とACKを照合しました。

## v0.1.2から更新する

本体はamitoki 0.2以降を使えます。本体の再ビルドは不要です。対象DBを使うamitokiを停止してから、プラグインを更新します。

```bash
amitoki plugin relay update postgres
~/.local/share/amitoki/plugins/postgres/amitoki-plugin-postgres --schema > schema.sql
psql "$AMITOKI_POSTGRES_URL" --set ON_ERROR_STOP=1 -f schema.sql
```

`AMITOKI_PLUGIN_DIR`・`XDG_DATA_HOME`を使う場合は、その配置先からSQLを取り出してください。接続変数名を変更している場合も読み替えてください。スキーマ更新後にamitokiを起動します。既存データと未ACKは維持します。大きな既存DBでの索引作成と、以前の版へ戻す手順は[保持期限と運用](https://github.com/amitoki/amitoki-plugin-postgres/blob/v0.2.0/docs/retention.md)に記載しています。

保持期間は容量上限ではありません。停止したノードの未ACKは残ります。DB再起動で占有ロックを失った場合には本体の明示再起動が必要です。

配布対象はLinux x86_64です。P2Pプラグインと中継IPC v1は変更していません。
